# 구현 계획 초안

아래 내용은 기획 초안이다. 후속 코드 작성의 구체적인 기술 구성, API 계약,
재부팅·알림 상태 처리는 [코드 작성 지시서](CODING_INSTRUCTIONS.md)를 따른다.

## 1. 첫 버전 범위

ESP32 한 대와 온습도 센서 한 개로 시작한다. 온도·상대습도·연결 상태를
서버에서 관리하고, 건조·회복·통신 이상 알림을 기존 헤르메스 봇으로 전달한다.

대시보드, 다중 방 관리, 장기 통계, 가습기 자동 제어는 후속 기능으로 둔다.

## 2. 미정 사항

- ESP32 보드 모델과 사용 가능한 GPIO.
- 센서 모델, 전원 전압, 통신 방식 및 라이브러리.
- Arduino/PlatformIO/ESP-IDF 등 펌웨어 개발 도구.
- 수집 서버의 실행 위치와 ESP32에서 접근할 네트워크 경로.
- 헤르메스에서 지원하는 알림 전송 경로와 대상 대화방 설정.
- 알림 기준, 측정 주기, 통신 이상 판단 시간, 재알림 여부.
- 장치 및 서버 재부팅 시 알림 상태 저장·복원 방식.

## 3. 측정과 전송

초안에서는 ESP32가 HTTP로 측정값을 전송하는 구성을 우선 검토한다.
인증과 전송 보호 방식은 실제 네트워크 구성에 맞춰 정한다.
인터넷에 수집 API를 직접 공개하는 것을 기본 전제로 삼지 않는다.

측정 데이터 예시이며, API는 아직 구현하지 않았다.

```json
{
  "device_id": "living-room-01",
  "temperature_c": 22.4,
  "humidity_rh": 37.0,
  "uptime_s": 3600,
  "sequence": 60
}
```

- `device_id`: 서버에 등록한 장치 식별자.
- `temperature_c`: 섭씨 온도.
- `humidity_rh`: 상대습도(%RH).
- `uptime_s`: 장치 부팅 후 경과 시간(초).
- `sequence`: 부팅 후 측정 순번. 재부팅하면 초기화될 수 있다.

서버는 수신 시각을 별도로 기록한다. 장치 시각 동기화가 확정되기 전에는
장치가 보낸 시각으로 건조 지속 시간이나 통신 이상을 판단하지 않는다.
재전송 중복을 식별하는 방법은 부팅 식별자 등을 포함해 구현 시 확정한다.

장치는 전송 실패 시 재연결·재시도하되 무한한 대기열을 만들지 않는다.
과거 측정값을 다시 보낼 경우 최신 상태와 혼동하지 않도록 구분한다.

## 4. 유효성 검증

- 등록된 장치의 인증된 요청만 수락한다.
- 숫자가 아닌 값, NaN, 무한대, 상대습도 0~100% 범위를 벗어나는 값을 거부한다.
- 온도 범위는 실제 센서의 사양을 확인한 뒤 정한다.
- 센서 읽기에 실패하면 임의의 정상값이나 이전 값을 새 측정값으로 전송하지 않는다.
- 잘못된 측정값이나 중복 요청으로 최신 유효 측정 시각을 갱신하지 않는다.
- 장치 식별자와 측정 순번만으로 인증을 대신하지 않는다.

## 5. 알림 상태

습도 상태와 연결 상태는 별도로 관리한다.

### 습도

1. 정상 상태에서 건조 기준 미만의 유효한 측정이 이어지면 대기를 시작한다.
2. 유효한 측정이 계속 수신되고 건조 지속 시간을 충족하면 건조 상태로 전환한다.
3. 건조 상태 진입 시 한 번 알린다.
4. 건조 기준과 회복 기준 사이에서는 건조 상태를 유지한다.
5. 회복 기준 이상이 되면 정상 상태로 전환하고 회복을 한 번 알린다.

건조 대기 중 정상 범위로 돌아오거나 측정이 끊기면 지속 시간 계산을 초기화한다.
유효한 최신 측정값이 없을 때에는 건조·회복 알림을 새로 만들지 않는다.

### 연결

1. 서버 시작 후 초기 수신 유예 시간을 둔다.
2. 유예 시간이 지나도 첫 측정이 없거나, 마지막 유효 측정 이후 제한 시간을
   초과하면 통신 이상을 한 번 알린다.
3. 유효한 측정이 다시 수신되면 연결 회복을 한 번 알린다.
4. 통신 이상 점검은 수신 요청과 별개로 주기 실행해, 장치가 완전히 꺼져도 감지한다.

알림 전송 실패와 센서 상태 변화는 구분한다. 헤르메스 장애로 전달하지 못한
알림은 재시도 상태를 남기고, 오래된 알림이 회복 알림 뒤에 도착하지 않도록 한다.
재시작 후 알림을 무조건 다시 보내지 않도록 상태 저장 방식을 정한다.

## 6. 헤르메스 연동

- 운영 중인 헤르메스의 전송 경로를 먼저 확인한다.
- 센서 측정마다 LLM을 호출하지 않고 서버에서 수치와 시간을 비교한다.
- ESP32에는 헤르메스 봇 토큰을 저장하지 않는다.
- 대상 대화방과 인증값은 서버의 비공개 설정으로 관리한다.
- 실제 시험 알림은 사용자에게 시험임을 알 수 있는 문구로 전송한다.

현재 초안 작성 단계에서는 운영 헤르메스 설정이나 기존 알림 정책을 변경하지 않는다.

## 7. 검증 및 완료 기준

- [ ] 실제 보드·센서 모델과 배선 기록.
- [ ] 실물 센서 측정값을 시리얼 출력으로 확인.
- [ ] ESP32 → 서버 전송 및 최신 유효 측정값 저장 확인.
- [ ] 잘못된 값과 인증 없는 요청 거부 확인.
- [ ] 건조 지속·중간 회복·기준 경계에서 상태 전환 검증.
- [ ] 같은 상태에서 중복 알림이 발생하지 않는지 검증.
- [ ] Wi-Fi 단절·센서 오류·장치 꺼짐 감지 및 복구 검증.
- [ ] 장치·서버 재부팅 후 상태 처리 검증.
- [ ] 헤르메스 전송 실패·재시도 동작 검증.
- [ ] 실제 텔레그램에서 시험 알림 수신 확인.
- [ ] 집에서 센서 설치 위치와 가습기 사용 전후 측정 추이 확인.

각 결과는 모의 입력, 서버 동작, 실제 장치, 실제 알림 수신으로 나누어 기록한다.
아직 수행한 검증은 없다.
